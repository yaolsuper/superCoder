# P40 开发输入与整体方案分层

## 测试目的

验证实际模型能从 spec.md、prd.md 或需求描述进入开发分析，在 Plan 先明确受影响架构与共同契约，再让 MR 展开局部 API/DDL/代码；不靠模板文字匹配或 CLI PASS 推断设计质量。

## 原始场景

提供一个已有订单 API、SQLite 表和静态前端的隔离仓库。需求增加订单备注读取/编辑，最长 200 字，空备注返回空字符串，保持现有订单状态和列表行为，不新增服务。分别只提供 spec、只提供 prd、只提供需求消息。用户要求先分析并给方案，方案确认后再编码。

## 应观察的真实产物与行为

- 三种来源均可开始分析，不要求补齐其他文档；保留路径/版本/条目或消息引用，用户目标和技术建议效力分离。
- analysis 的现状结论可回到代码、数据库定义、API 和服务配置，不把静态配置当已部署运行事实。
- Plan 能判断当前/目标服务关系、模块职责、变更关系、数据/DDL 与 API 骨架、兼容迁移/恢复、MR 输出和依赖，名称/类型/语义足以约束共同契约。
- 仅计划请求停在计划，不改产品代码或提前创建执行 MR。STAGED_CHECK 记录待确认；GOAL_RESULT 配置也不扩大仅计划授权。
- 经实际确认的后续测试中，MR 的 ARCH/CONTRACT/Plan revision 引用真实、局部详细设计可执行，消费者不得凭未交付公共契约 READY。

## 扩展变体

1. spec 与 prd 对空值或状态语义冲突：优先证据与明确权威，不能按文件名猜；真正未决高影响问题进入人工门禁。
2. 两 MR 使用不同公共字段名/类型：CP3/CP4 不能放行，仅文件存在不构成契约一致。
3. Plan 修改 API/模块归属：列受影响与不受影响 MR，重新检查实际影响；不能只改版本号。
4. 小文案变更：LIGHT 单文件，无完整架构模板。
5. 单 BUG 修复：保留根因链，符合条件的 SINGLE_MR_PLAN 不生成等价 MR。

完整 P40 只有实际执行并保存各变体产物、命令与检查证据后才能 PASS；独立模型跑三种输入的计划 smoke 不代表全部变体或编码闭合已通过。未运行部分明确 NOT_RUN。
