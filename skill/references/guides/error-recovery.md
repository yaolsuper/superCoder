# 错误恢复机制详解

本文档详细说明 Coder 开发执行技能的错误恢复机制，包括重试策略、回滚协议、状态恢复和升级策略。

## 1. 重试策略

### 1.1 可重试的偏差类型

| 偏差类型 | 是否可重试 | 最大重试次数 | 重试条件 |
|---|---|---|---|
| TEST_FAILURE | 是 | 2 次 | 失败在当前 MR 范围内，且有明确修复方向 |
| TOOLING_FAILURE | 是 | 1 次 | 可能是临时环境问题（如网络超时、锁文件） |
| CROSS_MR_ISSUE | 否 | - | 必须登记偏差，归属对应 MR |
| ENV_BLOCKER | 否 | - | 环境不可用，必须人工介入 |
| REQUIREMENT_CHANGE | 否 | - | 需要重新评审需求 |
| UNKNOWN_RISK | 否 | - | 风险不明确，等待评审 |

### 1.2 重试流程

```
验证失败
    ↓
分析失败类型
    ↓
是否可重试？
    ├─ 否 → 登记偏差 → 停止
    └─ 是 → 分析失败原因
               ↓
        执行小范围修复（仅限当前 MR 范围）
               ↓
        重新运行验证命令
               ↓
        验证通过？
        ├─ 是 → 继续后续流程
        └─ 否 → 重试次数 < 最大重试次数？
                    ├─ 是 → 返回"分析失败原因"
                    └─ 否 → 登记偏差 → 停止
```

### 1.3 重试示例

#### 场景：单元测试失败

```markdown
## 验证重试记录

### 第一次失败
- 失败命令: `mvn test`
- 失败原因: `UserServiceTest.testCreateUser` 断言失败
- 影响范围: 当前 MR 内（UserService 修改导致）
- 处理动作: 修复 UserService 中的用户创建逻辑
- 重试结果: 通过

### 重试次数统计
- 当前重试次数: 1
- 最大允许次数: 2
- 是否允许继续重试: 是
```

#### 场景：工具链失败

```markdown
## 验证重试记录

### 第一次失败
- 失败命令: `mvn checkstyle:check`
- 失败原因: Maven 仓库连接超时
- 影响范围: 环境问题，非代码问题
- 处理动作: 等待 5 秒后重试
- 重试结果: 通过

### 重试次数统计
- 当前重试次数: 1
- 最大允许次数: 1
- 是否允许继续重试: 否
```

### 1.4 重试等待策略

使用指数退避策略：

```
第 1 次重试：等待 5 秒
第 2 次重试：等待 10 秒
第 3 次重试：等待 20 秒（如果配置允许）
```

可通过项目配置调整：

```yaml
deviation:
  retry:
    enabled: true
    max_retries: 2
    retry_delay_seconds: 5
    backoff_multiplier: 2  # 指数退避倍数
```

## 2. 回滚协议

### 2.1 触发回滚的条件

必须在以下情况进入回滚决策，不得继续实现：

1. **路径越界**：修改了 `forbidden_paths` 中的文件
2. **验证失败且无法修复**：达到最大重试次数仍失败
3. **HIGH 风险偏差**：遇到无法立即解决的 HIGH 风险
4. **架构级偏差**：发现设计与实现严重不符
5. **数据安全风险**：可能造成数据丢失或损坏

### 2.2 回滚策略

按优先级选择恢复策略。任何会丢弃用户修改、清理目录、重置工作区或改写提交历史的动作，都必须先说明影响范围并获得明确授权。

#### 策略 1: 精确文件恢复（推荐）

只恢复确认由本轮任务造成、且命中越界或失败原因的文件。优先使用补丁反向修改、最小范围手动恢复或项目明确提供的非破坏性恢复命令。

优点：
- 可精确控制回滚范围
- 避免误删用户或其他执行者的修改
- 易于记录恢复原因和结果

#### 策略 2: Git 辅助恢复

当需要借助 Git 恢复文件时：

1. 识别需要回滚的文件
2. 确认这些文件的修改全部来自当前任务
3. 说明将要执行的 Git 命令和影响
4. 获得用户明确授权
5. 执行后验证工作区状态

适用场景：
- 越界文件必须恢复
- 当前任务修改需要整体撤销
- 工作区不存在其他人未提交修改

#### 策略 3: 脚本回滚

仅当项目配置明确允许，并且脚本影响范围清晰时，使用项目配置的回滚脚本：

```yaml
deviation:
  rollback:
    enabled: true
    strategy: "script"
    rollback_script: "scripts/rollback.sh"
```

回滚脚本应具备以下特征：

- 支持 dry-run 或预览
- 只处理当前 MR 范围内资源
- 不删除未列明目录
- 不输出密钥或敏感配置
- 执行前后都能产出可验证状态

### 2.3 回滚流程

```
触发回滚条件
    ↓
确定回滚范围
    ├─ 单文件回滚
    ├─ 多文件回滚
    └─ 当前任务范围恢复
    ↓
选择回滚策略
    ├─ 精确文件恢复
    ├─ Git 辅助恢复
    └─ 脚本回滚
    ↓
确认是否需要用户授权
    ↓
执行回滚
    ↓
验证回滚结果
    ├─ git status 检查
    ├─ 验证关键功能
    └─ 确认无残留修改
    ↓
记录回滚信息
    ├─ 回滚原因
    ├─ 回滚范围
    ├─ 回滚时间
    └─ 回滚结果
    ↓
更新 MR 状态为 BLOCKED
    ↓
输出偏差报告
```

## 3. 状态恢复

### 3.1 会话中断恢复

当执行过程中断（如会话丢失、网络断开），按以下流程恢复：

```
重新建立会话
    ↓
读取 coder-current-task.md
    ├─ 获取当前 MR ID
    ├─ 获取当前状态
    └─ 获取最后执行步骤
    ↓
检查 git 状态
    ├─ git status
    ├─ git diff --name-only
    └─ git log -n 5
    ↓
判断恢复策略
    ├─ 状态为 PENDING/READY → 从头开始
    ├─ 状态为 RUNNING → 检查是否有未提交修改
    │   ├─ 有修改 → 执行差异检查 → 继续验证
    │   └─ 无修改 → 从实现步骤继续
    ├─ 状态为 VERIFYING → 重新执行验证
    ├─ 状态为 BLOCKED → 查看偏差记录 → 等待处理
    └─ 状态为 ACCEPTED → 检查是否可进入下一 MR
    ↓
更新执行记录
    ↓
继续执行或请求人工介入
```

### 3.2 状态恢复检查清单

```markdown

- 工作区干净: 是 / 否

- 推荐恢复点:
```

### 3.3 检查点机制

推荐在关键步骤后保存检查点：

```yaml

    status: "passed"
```

## 4. 偏差升级策略

### 4.1 升级触发条件

必须在以下情况立即升级（停止并请求人工介入）：

| 条件 | 风险等级 | 处理方式 |
|---|---|---|
| 连续 3 次执行失败 | HIGH | 停止，请求评审 |
| 遇到 ENV_BLOCKER | HIGH | 停止，通知环境负责人 |
| 遇到 REQUIREMENT_CHANGE | HIGH | 停止，请求产品确认 |
| HIGH 风险无处理方案 | HIGH | 停止，等待评审 |
| 架构级偏差 | HIGH | 停止，请求架构师介入 |
| 数据安全风险 | CRITICAL | 立即停止，通知 DBA |

### 4.2 升级流程

```
触发升级条件
    ↓
停止当前操作
    ↓
收集偏差信息
    ├─ 偏差类型
    ├─ 偏差描述
    ├─ 影响范围
    └─ 已采取动作
    ↓
输出升级报告
    ├─ 问题摘要
    ├─ 风险分析
    ├─ 建议处理方案
    └─ 需要决策项
    ↓
通知相关人员
    ├─ 技术负责人
    ├─ 产品负责人（如涉及需求）
    └─ 环境负责人（如涉及环境）
    ↓
等待决策
    ↓
根据决策继续或终止
```

## 5. 项目配置示例

```yaml
deviation:
  # 重试配置
  retry:
    enabled: true
    max_retries: 2
    retry_delay_seconds: 5
    backoff_multiplier: 2
    retryable_types:
      - "TEST_FAILURE"
      - "TOOLING_FAILURE"
  
  # 回滚配置
  rollback:
    enabled: true
    strategy: "file_restore"  # file_restore / manual / script
    rollback_script: "scripts/rollback.sh"
    auto_rollback_on:
      - "path_violation"
      - "max_retries_exceeded"
      - "high_risk_deviation"
  
  # 升级配置
  escalation:
    immediate_escalation_risks:
      - "ENV_BLOCKER"
      - "REQUIREMENT_CHANGE"
      - "UNKNOWN_RISK"
    max_consecutive_failures: 3
    notify_on_escalation:
      - "tech_lead"
      - "product_owner"
  
  # 检查点配置
  checkpoints:
    enabled: true
    save_after_steps:
      - "startup_gate"
      - "change_plan"
      - "implementation"
      - "verification"
```

## 6. 最佳实践

### 6.1 重试最佳实践

1. **明确重试条件**：只在可预期的临时故障时重试
2. **限制重试次数**：避免无限重试浪费时间
3. **记录重试原因**：便于后续分析
4. **使用指数退避**：避免频繁重试加重问题

### 6.2 回滚最佳实践

1. **优先精确文件恢复**：只恢复确认由当前任务造成的问题文件
2. **回滚前备份状态**：防止误操作
3. **验证回滚结果**：确保完全恢复
4. **记录回滚信息**：便于后续分析

### 6.3 状态恢复最佳实践

1. **保持任务文件最新**：及时更新状态
2. **使用检查点机制**：便于断点恢复
3. **定期提交代码**：减少丢失风险
4. **记录关键决策**：便于理解上下文

### 6.4 升级最佳实践

1. **及时升级**：不要试图解决超出能力范围的问题
2. **提供完整信息**：便于决策
3. **给出建议方案**：提高决策效率
4. **跟踪升级结果**：闭环管理
