# Coder 代码审查与质量审核协议

用户明确要求 superCoder 代码审查、质量审核、回归风险、放行判断或 MR review，或当前交付链需要内部实际 diff review 且无可用原生能力时，读取本文件。普通独立 code review / 代码评审请求优先使用当前环境原生能力，不被内部自动 review 路由抢占。review 本身不修改产品代码；独立 review 请求需用户授权修复后切换到 execution，交付链内已授权的范围内修复由执行者按契约与 pre-edit guard 处理。

代码审查和质量审核必须严格控制逻辑，防止过度泛化。审查目标不是限制模型发现问题的能力，而是要求每个结论可复核、可定位、可验证。

已进入 superCoder 交付链的内部实际 diff review 按 `../../superCoder/references/shared/advancement-mode.md` 自动执行，优先使用原生 review，无可用能力时使用本协议，不需要每个单元重复点名本技能。这一内部调用不改变普通独立 code review 的路由；质量证据与阶段启动授权分别记录。
需要输出批准、条件批准、阻断，或与 Checkpoint / Ledger Audit 组合时，读取 `skills/superCoder/references/shared/decision-contract.md`。Review 负责质量 findings、严重度和证据，不复制账本完整性、Gate epoch 或 CP5 的判定规则。
如果审查对象是本 Skill 生成的分析报告、实施计划、MR 文件、执行记录或验收决策等正式产物，还必须同时使用 `skills/superCoder-checkpoint/references/checkpoint.md`，并输出 Checkpoint 结论。
如果审查对象是 BRD、PRD、ADD、LLD、DBD、MR 或 Coder 正式产物，必须读取 `skills/superCoder-checkpoint/references/document-review-checklist.md`，先判定文档/产物类型，再使用对应场景 checklist；不得只使用通用审查原则给出放行结论。

## 审查原则

- 先给发现，再给摘要。
- 只报告有明确证据、可复现路径或可解释推理链的问题。
- 每个问题必须说明影响范围、风险等级、证据来源和建议验证方式。
- 区分事实、推断和假设；推断必须说明前提，假设必须列入待确认。
- 不得把单个文件、单个调用点、单次日志或局部模式直接泛化为全局问题，除非审查范围已覆盖全局。
- 不得用风格偏好替代质量问题；除非风格差异会导致可维护性、兼容性、性能、安全或行为风险。

## 方案与核心机制审查

审查方案或包含机制变化的代码时，按以下方法验证当前设计；仅有文案、格式等修改时说明不适用原因，不强行设计实验。正式技术产物的 Reviewer 同样使用本节。

### 从第一性原理重建目标

- 从用户目标、上游验收标准和代码契约提取可观察结果、硬约束与必须保持的不变量，注明来源；当前实现和作者解释只是待审查对象，不是需求依据。
- 在这些约束下推导能满足目标的最小方案，再对照当前方案，指出每个新增机制解决的具体问题。无来源的前提列为开放问题，不自行增加需求。
- 识别核心机制：承担关键正确性、安全、数据一致性或性能主张，移除或替换后可能改变验收结果的机制。为每个核心机制记录“主张 → 适用前提 → 可观察指标或不变量 → 证据”；不能只按文件数量或代码规模判断。

### 对抗性审查

- 主动寻找能推翻主张的反例：根据实际调用链选择边界输入、失败路径、时序/并发、状态变化、依赖失效或兼容场景，追踪触发条件到可观察后果；不机械套用所有场景。
- 同时挑战方案和反对意见：核对反例是否符合真实契约、是否已有防护，避免把不可能输入或已处理路径写成缺陷。
- 报告已证实的问题、被证据排除的关键反例和仍未验证的主张。未复现的风险不得升级为确定性缺陷；必须验证而缺证据时，可报告验证缺口。

### 按机制主张选择验证方法

先明确要证明的主张，再选择能直接检验它的方法。正确性、鉴权、事务、兼容性和边界规则使用针对性契约测试、失败/并发场景、故障注入或可复核调用链证据；性能改善、算法收益、机制贡献与“复杂机制不可替代”的主张使用有区分力的对照/消融实验。不为普通条件修正或已有安全保护机械删除机制做实验。

只覆盖成功路径的全量测试不能证明关键失败不变量，作者解释或未执行计划也不能替代必要实测。设计阶段检查可执行验证计划和下游任务；实现验收检查当前 revision 的适用证据，必要证据缺失仍为 Blocker。

### 需要比较贡献时的消融实验

消融实验用于检验机制的贡献和必要性，不能用“全量测试通过”、作者解释或静态阅读代替。

- 对承担贡献、性能或复杂度必要性主张的机制，比较完整方案与仅移除、关闭或替换该机制的简化方案；保持 revision、输入、环境、依赖和其他机制一致。无法独立移除时说明依赖关系，采用最小可解释的组合消融，不把组合效果归因于单个机制。
- 执行前确定验收指标、不变量和判定阈值，沿用已有目标，不依据结果事后挑指标。样本须覆盖机制声称生效的路径和相关失败边界；性能或随机结果需记录重复测量、波动及实际收益，不能以单次差异证明贡献。
- 正确性机制应在消融后暴露预期的不变量违反，并在完整方案中保持该不变量；性能机制应在满足同等正确性约束下显示达到验收阈值的改善。同时记录机制带来的资源、维护和兼容成本。
- 在隔离测试环境、临时副本或可逆测试开关中运行；不得为了消融关闭生产保护或直接修改被审产品代码。review 默认只读，实验需要超出授权范围的修改时，报告具体缺口和允许的补验证方式。
- 记录机制/主张、对照差异、revision/环境、样本、命令、预期结果、两组实际结果、证据位置和局限。已有实验仅在与当前 revision、机制和场景一致时可复用。
- 若消融后结果不变，先检查实验是否命中生效路径、样本和指标是否有区分力；有效实验仍无贡献时，应建议删除或简化机制，或收窄其主张，不以“以后可能用到”保留。
- 设计阶段尚无实现时，检查适用的对照计划及实现/验收任务承接，不标为已通过实验。需要贡献比较的实现验收缺有效对照、结果不支持主张或违反必要不变量时，构成 Blocker；正确性类机制按上节的针对性证据验收，不机械要求消融。

### 奥卡姆剃刀与高内聚、低耦合

- 在满足相同目标、硬约束和不变量的候选方案中，优先选择机制、状态和依赖更少的方案。逐一检查新增抽象、分支、配置、持久化状态和依赖是否有当前需求或实验依据；复用现有能力前先确认语义和契约相同。
- 高内聚：模块围绕同一职责和变化原因组织，业务规则及其不变量有明确归属；指出职责混杂导致的具体修改、测试或一致性风险。
- 低耦合：检查依赖方向、接口契约、状态所有权和副作用边界，定位循环依赖、共享可变状态、跨模块访问内部实现及同一规则的多处同步修改。
- 简化不得删除必要的鉴权、事务、兼容或错误处理。行数、类数、设计模式和“看起来更优雅”不构成结论；每项结构建议须说明可删/可合并内容、保留的契约、变化影响和验证方式，不扩展为无关重构。

## 输入范围

审查开始前必须明确：

- 审查对象：分支、diff、文件、MR、提交、目录或用户给定片段。
- 审查目标：正确性、安全、兼容性、数据风险、性能、可维护性、测试覆盖或放行判断。
- 文档/产物类型：BRD / PRD / ADD / LLD / DBD / MR / ANALYSIS / PLAN / CURRENT_TASK / EXECUTION_RECORD / ACCEPTANCE_DECISION / 不适用。
- 使用的场景 checklist：来自 `skills/superCoder-checkpoint/references/document-review-checklist.md` 的具体 checklist 名称。
- 审查范围：已读取文件、已检索路径、未覆盖路径。
- 排除项：用户要求忽略的问题、非本轮关注的模块或已知外部失败。
- 验证方式：静态阅读、命令验证、日志验证、接口复现或无法执行验证的原因。

如果审查对象或范围不明确，先做有界发现；仍无法确认时，输出缺失信息，不得给出放行结论。
如果文档/产物类型无法判断，输出类型判定问题；不得用“通用 Review”替代场景 checklist。

审查中的命令和内容查询必须有界过滤。不得使用无范围 `git diff`、无 `--tail` / 无时间窗口的 `docker logs`、`docker logs -f`、无界全文读取或无边界递归搜索。审查 diff 时先使用 `git diff --name-only` 或 `git diff --stat` 定位文件，再对具体文件执行 `git diff -- <path>`；审查日志时必须使用 `--tail`、`--since` 或关键词过滤。

## 证据要求

每个发现至少包含以下证据之一：

- 文件和行号。
- 调用链或数据流路径。
- 配置、接口、数据库或外部依赖的契约依据。
- 测试失败、日志摘要、命令输出摘要或可复现步骤。
- 与当前任务验收标准、MR 目标或路径守卫的冲突。

证据不足时，只能写入“开放问题”或“待验证风险”，不能作为确定性缺陷。

## 风险分类

推荐使用以下分类：

| 分类 | 含义 |
|---|---|
| CORRECTNESS | 行为错误、边界条件错误、空值、并发、状态机或异常处理问题 |
| COMPATIBILITY | API、数据结构、配置、数据库、浏览器、运行时或版本兼容问题 |
| SECURITY | 鉴权、权限、注入、密钥、敏感信息、越权或供应链风险 |
| DATA_RISK | 数据丢失、重复写入、脏读、迁移、回滚或一致性风险 |
| PERFORMANCE | 明显的复杂度、资源、锁、IO、网络或渲染性能风险 |
| MAINTAINABILITY | 会导致后续修改高风险的重复、隐式契约或不可测试结构 |
| TEST_GAP | 当前风险缺少必要测试或验证路径 |

- 未使用专项 Checklist 的原因：无 / 不适用 / 类型无法判断

## 方案与机制验证（涉及方案或机制变化时）

- 目标 / 硬约束 / 不变量及来源：
- 满足相同约束的最小方案及当前方案差异：

如果没有发现问题，应明确说明“未发现阻断问题”，并列出剩余测试缺口或未覆盖范围。不得把未覆盖范围描述成已验证通过。

## 放行判断

只有满足以下条件时，才允许给出可放行结论：

- 审查范围与用户目标匹配。
- 高/中风险发现已解决、归档或被用户明确接受。
- 必要验证已执行，或未执行项有明确且可接受的原因。
- 测试缺口不会阻断当前任务验收，或已作为风险列出。
- 未把局部阅读结论泛化为全局质量结论。
- 方案或机制变化完成目标、反例、复杂度和模块边界审查；设计具有适用的验证计划，实现具有支撑对应主张的当前证据，贡献/性能主张具有有效对照结果。
- 若审查对象涉及产品代码修改或执行记录，必须取得 Ledger Audit 的账本事实；需要最终交付时再交由 Checkpoint CP5 组合裁决。Ledger Audit 非 PASS 时按统一决策契约列为 Blocker，不得放行。

否则结论必须是“不建议放行”或“无法给出放行结论”，并说明阻塞原因。
