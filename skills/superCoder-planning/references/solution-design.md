# 开发输入与整体方案设计

本协议负责上游输入、Plan 架构骨架与 MR 详细设计的分工。STANDARD / CONTROLLED 生成或修订分析、Plan、MR 时读取；执行恢复只读当前 Plan、MR 及其引用的受影响章节，不默认加载全项目设计。

## 开发输入

- 支持 `spec.md`、`prd.md` 或一段需求描述；不要求固定文件名、PRD Agent、全部文档同时存在或补齐产品文档后才能分析。进入开发交付的触发边界仍由主技能决定，文件存在本身不触发实施。
- 在 analysis 记录来源清单：稳定来源 ID、文件路径及可获得的 revision/digest 和章节/条目，或原始消息引用；提炼目标、非目标、业务规则、验收标准和真实约束。上游缺少编号时可建立本地 `REQ-###`，不得伪造上游编号或已确认状态。
- 区分明确需求/硬约束、上游设计建议、代码现状与推断。spec 中的服务、模块、API、表结构不自动成为当前系统事实，也不自动成为唯一实现。prd 含技术建议时同样核对其来源与约束效力，不因为文档类型删除信息。
- 多来源冲突时记录冲突点及范围，依据明确版本/权威来源和用户指令裁决，不凭文件名认定 spec 永远高于 prd。系统证据能回答的先调查；无法解决且会改变业务语义、范围、验收或高风险边界的决策按 human-confirmation-gate 处理。
- 有界核对受影响代码、API/Schema、数据库定义、服务配置、依赖和测试。涉及实际运行拓扑、已应用 DDL 或已部署版本时使用可获得的运行/部署证据；仓库声明不冒充已运行事实。运行证据缺失时标明限制，只有影响当前实施判断时阻断。

## 分层职责

| 层 | 权威职责 | 下游使用方式 |
|---|---|---|
| 上游 spec / prd / 需求消息 | 需求来源、业务目标、行为与验收；技术约束的效力按来源确认 | analysis 引用，不重新生成 PRD |
| analysis | 有证据的当前结构、目标差距、影响与可行性 | Plan 从通过分析的结论推导 |
| Plan | 受影响系统的整体架构、变更关系、跨 MR 共同契约、迁移策略与交付边界 | MR 引用架构项和契约，不复制全局正文 |
| MR | 当前交付单元的详细设计、精确 API/DDL/代码、Tasks 与验证/回退 | Task 消费 `DESIGN-###`；实现不得静默改写上游约束 |

Plan 的粗粒度意味着局部实现下沉，不意味着跨 MR 的接口、数据语义、依赖或一致性规则含糊。整体架构限于受影响系统及必要邻接关系，不要求重画无关服务；已有架构文档、IDL、Schema 或 ADR 可直接引用并核对版本。

## Plan 的整体架构与变更设计

生成 Plan 时读取 `../../superCoder/assets/templates/implementation-plan.md` 所需章节。按真实影响选择下列内容；未涉及的维度不创建空表，不为填模板新增服务、表或中间件。没有结构变化时写清现有结构复用及依据。

| 内容 | Plan 必须明确的骨架 | 下沉到 MR 的细节 |
|---|---|---|
| 当前/目标服务结构 | 受影响服务及职责、运行/部署证据的范围，新增/修改/复用关系、调用/事件/部署变化 | 当前服务接入、配置和实现位置、运行与部署验证 |
| 功能模块拆分 | 按能力和不变量划分职责，模型/数据归属、输入输出、上下游依赖 | 类/方法、文件、局部流程与算法 |
| 变更关系 | 变更前后及消费者影响；关键数据流、控制流、副作用顺序，用关系表或必要图表达 | 具体调用点、适配与回归路径 |
| 数据库/DDL | 实体、关系、核心字段语义和约束、读写归属、迁移/回填与兼容策略；关键新增/修改/删除对象 | 完整 DDL/migration、索引、回填实现、执行和回退验证 |
| API 输入输出 | HTTP/RPC/事件边界；核心输入输出字段及类型/语义、成功/空结果/错误、鉴权与幂等，版本/兼容约定 | 完整 OpenAPI/Proto/DTO/Schema、校验、样例、签名与契约测试 |
| 事务与相关 NFR | 一致性/并发/重试/补偿/外部副作用及相关性能、安全、可观测性约束，有来源与验证办法 | 当前 MR 的具体机制和测试 |
| 实施与恢复 | MR 输入输出、依赖、发布/迁移顺序、混合版本条件、停止/回退策略和必要取舍 | 当前 MR 的执行步骤与验收证据 |

架构项使用稳定 `ARCH-###`，关联需求/分析来源、现状依据、目标变化、消费者/数据/发布影响及承接 MR。列出替代方案或直接复用的依据，便于 Leader 判断目标对齐、必要性和实施可行性；不把尚未实施的方案写成已验证结果。

## 跨 MR 契约与拆分

- 被多个 MR 消费的 API、字段、事件或状态规则，在消费者进入 READY 前必须有唯一、可解析的权威定义：记录稳定 `CONTRACT-###`、定义位置及 revision/digest、语义/兼容规则、生产者和消费者。已有协议直接复用；不得让各 MR 独立发明共同字段或双写完整定义。
- Plan 中确定公共名称、类型、语义和兼容边界，或明确交给前置契约 MR 交付后再放行消费者。完整 DDL/API 声明仍可保存在仓库已有契约文件或对应 MR；不用为了契约强制增加文档 MR。
- Plan 可通过稳定锚点权威定义必要共同契约，不要求额外 `architecture.md` / ADD / LLD / DBD 文件。MR 引用定义及其适用版本，保留局部设计。单 BUG 的 SINGLE_MR_PLAN 仍按 artifact-model 使用同一文件内不同职责小节，不生成等价 MR。
- 从职责、契约、验证、交接和发布/回退边界推导 MR。不能只按数据库/后端/前端机械切分，也不要求每个模块单独成为 MR；每个 MR 的可观察输出、依赖条件、验证和恢复办法必须明确。
- 来源链为需求/分析结论 → Plan 架构与契约项 → MR 的 `architecture_refs` / `contract_refs`、`based_on_plan_revision` → `DESIGN-###` → Task → 实际变更与验证。与当前 MR 无关的全局设计不展开。

## 检查与修订

- Plan CP2 核对现状证据、目标/非目标、整体变更关系、受影响设计维度、公共契约与迁移/恢复策略是否足以判断；缺失影响实施的骨架返回 `SOLUTION_DESIGN_REQUIRED`，不得确认方案。
- CP3 核对来源、架构/契约项与 MR 输出/依赖映射，无遗漏、冲突或无来源扩张；不可解析引用或消费者使用不同公共契约返回 `PLAN_MR_DESIGN_MISMATCH`。
- CP4 核对当前 MR 的详细设计承接有效 Plan 和公共契约，实际依赖交付及版本可用，API/DDL/设计足以执行。待交付公共契约不能凭预期或 DONE 标签放行消费者。
- Plan、输入版本、公共契约或整体架构发生实质变化时，停止受影响实施，修订来源/Plan，列出受影响与不受影响 MR 及依据；重新检查受影响 CP2/CP3/CP4、契约 revision 和启动授权。不得仅改 `based_on_plan_revision` 伪装已对齐，也不因无关修改强制重做全部 MR。
- STAGED_CHECK 由 Leader 按 advancement-mode 确认整体方案与当前单元启动，再在后续完整单元边界确认；已有匹配授权不重复确认。GOAL_RESULT 在授权目标内自动审查方案/依赖，关键人工决策仍走既有门禁。架构审查不另设默认人工审批，也不扩大合并/部署授权。
- LIGHT 支持相同输入来源，但只在 light-task.md 记录来源与最小分析/方案；真实接口、数据、架构或依赖变化先升级风险模式再生成所需整体方案，不机械套用完整模板。
